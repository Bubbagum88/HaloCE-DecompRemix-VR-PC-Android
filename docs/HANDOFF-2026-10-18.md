### 8. Steam Frame: research done, fixes not started

Both APKs reportedly fail to launch. Sources:
[frame-control PR #20](https://github.com/saphid/frame-control/pull/20) (Lepton = Valve's Waydroid-based
Android layer). Four known blockers:
1. **Launcher:** Lepton starts only an activity with MAIN+LAUNCHER, never an `<activity-alias>`.
   - Our main manifest has LAUNCHER on the launcher activity. Check the VR flavour's manifest
     (`port/android/app/src/vr/AndroidManifest.xml`): does it use only `com.oculus.intent.category.VR`, or
     LAUNCHER on an alias? Make the launch activity a real activity with MAIN+LAUNCHER in both APKs.
2. **OpenXR:** SteamVR's Android runtime is OpenXR 1.0 only.
   - A 1.1 apiVersion fails with `XR_ERROR_API_VERSION_UNSUPPORTED`.
   - `host_xr.c` should request 1.0, or retry with `XR_MAKE_VERSION(1,0,x)`, and avoid 1.1-only calls:
     `xrLocateSpaces` (use the KHR one), `grip_surface` (use `palm_ext`), 1.1-only interaction profiles.
3. **Refresh rate:** SteamVR refuses fixed rates (`XR_ERROR_DISPLAY_REFRESH_RATE_UNSUPPORTED_FB`). Make
   refusal non-fatal and keep the current rate.
4. **Missing services:** Lepton lacks some Android services (clipboard crashed a Godot app). Our SDL patch
   guards the clipboard service already (Test15); check other services the launcher Java uses.

Also check:
- the flat APK fails too: point 1 and services are the likely cause;
- `uses-feature` `glEsVersion` 3.0 (Lepton mounts Mesa/Zink);
- the native ABI is arm64 (done);
- 16 KB page alignment of `.so` LOAD segments: unknown for the Frame; checking is cheap
  (`llvm-readelf -l`), and our guest memory code assumes 4 KB pages (`host_memory.c` `PAGE`).

The owner wants this fixed from research, not blocked on a log. Ask for a log only to confirm.

## How to build and test

- **Windows PC VR:**

  ```powershell
  $ninja = (Get-ChildItem "$env:LOCALAPPDATA\Microsoft\WinGet\Packages" -Directory -Filter "Ninja-build*" | Select-Object -First 1).FullName
  $env:PATH = "C:\Program Files\LLVM\bin;$ninja;$env:PATH"
  Set-Location D:\HaloQuest\HaloCE-Quest-VR
  python configure.py --portable   # again after any WSL/Android configure
  ninja windows_vr
  ```

- **Null-driver run:**
  - Use `& D:\HaloQuest\_scratch\t72\pcvr_run.ps1 -Name N -Env "..." -Commands @() -Delay 15 -Seconds 70
    -DumpFrame F`. It edits SteamVR's settings and restores them; check "restored steamvr.vrsettings: True".
  - Upright views: `HALO_VR_FORCE_RENDER=true;HALO_VR_DIAG_YAW=0.01`. The null driver's own head is rolled
    180°.
  - AR test: `HALO_NETWORK_TEST=host:bloodgulch;HALO_NETWORK_TEST_START=5;HALO_NETWORK_TEST_PICKUP=8;`
    `HALO_NETWORK_TEST_PICKUP_WEAPON=assault;HALO_VR_DIAG_FIRE_FRAME=1900;HALO_VR_DUMP_FRAMES=12`, with
    `-DumpFrame 2004`.
  - `_scratch/t72/contact_sheet.py dir out.png 1 360 4` builds a sheet of the dumped frames.
  - Delete dumps after use (D: has ~12 GB free).
- **Guest images:** `MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu-24.04 -- bash /mnt/d/HaloQuest/_scratch/compile67m.sh vr`
  (or `flat`). The log is `_scratch/compile67m_<flavor>.log`.
- **Full suite:** `wsl ... python3 tools/run-quest-checks.py`. Read "Failed suites".
- **Scripts that write repo files:** write bytes with LF. Windows Python text mode turns LF into CRLF. Shell
  heredocs mangle quotes and backslashes, so use the Write tool for scripts.
- **Never run two builds at once** (WSL process exhaustion).
