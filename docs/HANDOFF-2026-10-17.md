## What was found this session (verified on the SteamVR null driver)

- **The null driver's head is upside down.** It reports eye and head
  orientation (x y z w) = (0, 0, -1, 0), a 180° roll. Every earlier null-driver
  eye dump (and the mirror window the owner watched: "both are fucking
  flipped") showed the world upside down because of this. It is a test-rig
  artifact, not the game.
  - For upright test runs, set `HALO_VR_FORCE_RENDER=true` **and**
    `HALO_VR_DIAG_YAW=0.01`. A non-zero yaw makes `synthesize_views()` replace
    the runtime's pose.
  - Checked that way: eye source row 0 = sky, swapchain image row 0 = ground.
    That is correct for OpenXR GL images. Both eyes are upright in the dumps.
- **My first theory was wrong.** I thought SteamVR reset `glClipControl` on
  the game's context. `vr_runtime_state_restore()` in `d3d8_gl.c` never logged
  a change. **Remove it**, together with the `glIsEnabled` entries added to
  `gl.h`. It adds `glGet`/`glIsEnabled` queries on every state invalidate,
  which costs a sync on some drivers, and fixes nothing.
- **Upside-down menus/UI, the likely real cause (fix built, not yet seen on a
  menu).** On desktop GL the renderer keeps
  `glClipControl(GL_UPPER_LEFT, GL_ZERO_TO_ONE)` (`d3d8_gl.c` ~1596). That
  turns over every helper quad `vr_frame.c` draws into the eye images:
  vignette, world-anchored menus/HUD (`hud_program`), crosshair ×2, scope.
  GLES (the Quest) has no clip control, so it was right there.
  - The fix: `helper_draw_quad()` in `vr_frame.c` (~line 4636) switches to
    `GL_LOWER_LEFT, GL_NEGATIVE_ONE_TO_ONE` around those five draws
    (desktop only).
  - The HUD quad layer's own image (`vr-hud.bmp`) is upright.
  - **Still to verify:** a run with a menu or the world-anchored HUD showing,
    dumped upright.
- **The yellow rectangle (the "stretched flat graphic"), seen but not yet
  identified.**
  - Firing the plasma pistol in pulses sometimes shows a flat, solid,
    tilted yellow rectangle at the muzzle in both eyes, instead of a blended
    flash (runs fire2 and fire3). A few frames later the glow can look right
    (fire6).
  - Ruled out: lens flares. It stays with `HALO_GRAPHICS_LENS_FLARES=off`, and
    the sun's lens flare renders fine.
  - Suspects:
    - light volumes (`source/objects/widgets/light_volumes.c`, with the
      port's `rasterizer_widget_batch_sprites` batching);
    - particles or contrails whose texture alpha is ignored. A solid quad in
      the vertex colour looks like a texture or sprite-UV problem.
  - Quest 3 also gets the HIGH preset (`port/linux/game/vr_graphics.c`,
    `preset_for_headset`), so if the Quest is right, the difference is in the
    desktop GL path. That is still unproven: nobody has checked the Quest for
    it.
- **Floating grass:** not investigated yet. The Blood Gulch spawn view had no
  grass in frame. Detail objects are on at MEDIUM and HIGH.
  - Earlier suspect: Test72's kept quad index buffer for QUADLIST
    (`quad_index_bind`).
  - Look with `HALO_VR_DIAG_YAW` turned toward the green slopes, or on another
    map.

## How to build and test (Windows PC VR)

```powershell
$ninja = (Get-ChildItem "$env:LOCALAPPDATA\Microsoft\WinGet\Packages" -Directory -Filter "Ninja-build*" | Select-Object -First 1).FullName
$env:PATH = "C:\Program Files\LLVM\bin;$ninja;$env:PATH"
Set-Location D:\HaloQuest\HaloCE-Quest-VR
python configure.py --portable   # again after any WSL/Android configure
ninja windows_vr
```

The null-driver run (owner-approved). It edits
`C:\Program Files (x86)\Steam\config\steamvr.vrsettings` and restores it in
`finally`. The backup is `D:\HaloQuest\_scratch\t72\steamvr.vrsettings.backup`;
check after every run that the content matches.

```powershell
& D:\HaloQuest\_scratch\t72\pcvr_run.ps1 -Name NAME -Env "HALO_NETWORK_TEST=host:bloodgulch;HALO_NETWORK_TEST_START=5;HALO_VR_FORCE_RENDER=true;HALO_VR_DIAG_YAW=0.01;HALO_VR_DIAG_FIRE_FRAME=1900;HALO_GPU_TRACE=-2" -Commands @() -Delay 15 -Seconds 70 -DumpFrame 2003
```

- Log: `D:\HaloQuest\_scratch\t72\run-flat\stderr-NAME.txt`.
- Dumps (9 MB each): `D:\HaloQuest\_scratch\xbox_usa\vr-eye0.bmp`,
  `vr-eye1.bmp`, `vr-hud.bmp`.
- To view them:
  - `python -I D:\HaloQuest\_scratch\t72\bmp2png.py in.bmp out.png 720`
  - `bmp_crop.py in.bmp out.png x0 y0 x1 y1`
- **Delete the BMPs and PNG folders after use: D: has about 12 GB free.**
- Shot timing varies run to run, so the yellow rectangle is not in every dump.
  Make the dump fire a fixed few frames after a logged shot (`vr: shot (…)` is
  logged at `port/linux/game/vr_render.c:2105`), or retry other dump frames.
- Then read the `HALO_GPU_TRACE=-2` draw lines (texture formats, blend) for
  the rectangle's draw. Toggle `HALO_GRAPHICS_PARTICLES` /
  `HALO_GRAPHICS_CONTRAILS` to narrow it down.
- Test runs use scratch roots only (`HALO_DATA_ROOT=D:\HaloQuest\_scratch\xbox_usa`,
  saves under `_scratch\t72\run-flat\saves`), never the owner's `%APPDATA%`.
